# 免訓練快速驗證：善用「延遲與權重數值無關」的原理

## 問題現象

團隊想確認某個架構改動（例如調整某一層的通道數、拿掉某個分支、合併輸出節點）到底能不能改善邊緣裝置上的推論延遲，但完整訓練一輪往往要花上大半天甚至更久。如果每次架構調整都得先訓練完才能上板測速度，驗證週期會被訓練時間綁架，一天最多只能試一兩種改動，架構搜索的效率非常差。

## 為什麼會發生（原理說明）

多數邊緣 NPU 的推論延遲，本質上是由計算圖的結構決定的：張量形狀、運算元種類、記憶體搬移與資料重排的方式，這些在編譯階段就已經固定下來，屬於**靜態排程**的結果。**權重張量裡實際存的數值大小，通常不影響這個排程結果**——同一個架構不管权重是訓練到收斂的、還是隨機初始化的，走過硬體的計算路徑、記憶體存取模式都完全一樣，延遲自然也幾乎一樣。

這代表「這個架構改動能不能讓速度變快」跟「這個架構改動能不能讓模型學得好」其實是兩個可以獨立驗證的問題，前者根本不需要真的訓練，只要架構定義出來，用隨機初始化的權重直接匯出、編譯、上機測速度即可。

## 系統化排查步驟

1. **先在目標硬體上驗證這個假設本身成立**：拿同一個架構、兩組不同的權重（例如訓練到一半 vs 訓練完成），分別匯出編譯後上板測延遲，確認兩者數字幾乎一致，才能放心把這個技巧當作可靠的捷徑，而不是想當然爾。
2. **建立一條獨立於正式訓練流程的「快速通道」**：只需要架構定義 + 隨機初始化權重，就能跑完「匯出 → 編譯 → 上板量測延遲」整個流程，跟正式訓練管線解耦，改一版架構、測一次速度可以壓縮到幾分鐘等級。
3. **用這條快速通道做架構層面的設計空間搜索**：把候選的架構改動都先過一輪延遲測試，用實測數字排序，篩掉明顯沒有效益或效益不成比例的改動，只把真正值得投入訓練資源的候選留到最後。
4. **確定架構後才進入正式訓練**：延遲驗證只回答「這個架構值不值得訓練」，不回答「訓練出來準不準」，兩者順序不能顛倒，也不能互相取代。

## 一般性解法 / Checklist

- [ ] 使用這個技巧前，先在目標硬體上實測驗證「同架構不同權重延遲一致」這個前提，不要憑理論直接假設成立
- [ ] 建立獨立於正式訓練管線的「隨機權重 → 匯出 → 編譯 → 上板測延遲」快速驗證流程
- [ ] 架構搜索階段，優先用這條快速通道大量比較候選改動，篩選後才投入真正訓練
- [ ] 明確劃清這個技巧的適用邊界：只能驗證延遲/計算圖相關的問題，**不能**用來驗證準確率、量化誤差、校正資料代表性等任何跟實際權重數值/資料分佈有關的問題
- [ ] 準確率驗證仍須用真實訓練完成、真實校正資料跑過的模型，不可用隨機權重的結果替代
