# 系統化除錯方法論：區分算力瓶頸與系統瓶頸

## 問題現象

團隊在模型加入一個新功能分支後，發現上板實測的延遲增幅遠超預期——靜態效能估算工具算出來的增量只有個位數毫秒等級，但真實裝置端到端量測的增量卻是好幾倍。另一種常見情況是：延遲數字在對照測試環境下穩定，但部署到真實運行場景後，偶爾會出現遠超平常水準的延遲尖峰，而且尖峰只在特定條件下才出現，難以穩定重現。這兩種現象都容易讓人急著把問題歸咎到模型架構本身，但實際根因往往不在算力，而在別的地方。

## 為什麼會發生（原理說明）

靜態效能估算工具通常只對「計算量」（例如乘加次數）建模，對於其他成本來源——例如每個輸出節點的固定開銷、記憶體搬移與資料重排、只在特定訓練設定下才會啟用的額外分支——往往完全估不到，因為那些成本要在真正的硬體資料流路徑上才會顯現。這代表**任何跟靜態估算對不上的落差，都值得懷疑是估算工具的盲區，而不是急著解讀成「某個猜測中的機制」**。

偶發性的延遲尖峰則是另一種性質的問題：如果裝置上有多個子系統共用同一份有限資源（最典型是單核心 CPU），當某個跟推論無關的子系統（例如事件觸發時的畫面存檔、壓縮、上傳）被啟動，它會跟推論結果的後處理搶佔同一顆核心，造成該幀延遲飆升。這是**系統排程層級的資源競爭**，跟模型算得快不快完全無關，再怎麼優化模型架構都解決不了。

## 系統化排查步驟

1. **每個直覺猜測都要先量化「預期能解釋多少落差」，再去驗證**：用逐 op 效能分析工具量出詳細的耗時分佈，計算某個猜測的機制理論上能貢獻多少延遲，如果連數量級都對不上實測落差，這個猜測就該直接排除，不用再深究。
2. **確認你的量測路徑跟真正部署路徑一致**：有時候為了方便會用一個簡化的診斷連線（例如直接排線量測）去驗證改動有沒有效果，但這條路徑的雜訊或架構本身可能蓋過真正訊號，導致「看不出差異」的錯誤結論——只有跟正式部署完全一致的端到端路徑量出來的數字才能當作最終依據。
3. **設計單變量對照實驗**：每次只改一個變數，其餘保持一致，並且盡量放入一個「已知跟改動無關的成本」當作內部對照組，一旦這個對照組的數字也跟著大幅偏移，代表量測本身或環境有問題，而不是改動造成的。
4. **偶發尖峰要對照外部系統事件/log，而不是只看模型內部的效能分析**：把出現尖峰的樣本時間點跟系統其他子系統的觸發紀錄（I/O、編碼、網路上傳等）對齊，如果尖峰只在特定外部事件觸發時出現，優先懷疑資源競爭，而不是模型或演算法本身。

## 一般性解法 / Checklist

- [ ] 任何無法用靜態估算解釋的延遲落差，先假設是估算工具的盲區，不要急著採信第一個聽起來合理的機制假說
- [ ] 用逐 op 效能分析工具取得完整成本分解，再去驗證或排除假說，不要憑直覺推測
- [ ] 確認量測路徑跟真正部署路徑一致；圖方便用的診斷連線可能量不出真正的訊號
- [ ] 對照實驗一次只改一個變數，並保留至少一組已知結果的內部對照，用來偵測量測本身是否可信
- [ ] 偶發、非穩定重現的延遲問題，優先對照外部系統事件而非模型架構
- [ ] 多個子系統共用同一份硬體資源（單核心 CPU、共用匯流排）時，把資源競爭列為第一類懷疑對象，而不是最後才想到
