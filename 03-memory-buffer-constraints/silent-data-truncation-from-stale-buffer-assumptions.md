# DMA 定址限制與緩衝區容量假設過時排查

## 問題現象

有兩種常見但表現完全不同的「記憶體/緩衝區」問題：一種是模型送進硬體編譯器時直接報錯，指出某個位址超出定址上限，屬於編譯期就能發現的錯誤；另一種更棘手——模型能正常編譯、正常跑起來，統計數據看起來也正常，但某個下游功能（例如把推論結果疊加到畫面上）卻完全沒有輸出，而且沒有任何錯誤訊息，讓人誤以為是別的模組壞掉。

## 為什麼會發生（原理說明）

邊緣 NPU 平台的定址匯流排寬度通常是硬體固定的（例如 24-bit 定址對應 16MB 上限），這個限制在編譯期就會被工具鏈檢查出來，屬於「總量預算」問題：權重 + 推論過程中最大的中繼特徵圖緩衝區 + 輸出緩衝區，三者加總不能超過這個硬上限，模型解析度或類別數一旦提高，這個總量很容易超標。

比較隱蔽的是韌體/後處理端的固定大小緩衝區。這類緩衝區常量往往是在專案早期、以某個較小的輸出解析度為前提寫死的。當模型後來換成更高解析度或不同輸出形狀時，這個常量沒有同步更新；而許多韌體的邊界檢查為了「安全」，選擇在超出緩衝區大小時**直接跳過整個複製動作**，而不是報錯或截斷。結果就是：資料處理的統計路徑（例如記錄「這一幀分割出多少像素」的計數器）可能走的是另一條完全獨立的程式路徑，看起來一切正常；但真正把資料寫進顯示緩衝區的那一步，因為觸發了「超出容量就跳過」的保護邏輯，整個被靜默略過，畫面上自然什麼都看不到。

## 系統化排查步驟

1. **編譯期報錯的情況**：直接依照工具鏈提供的定址上限，反推目前模型的記憶體總需求（權重大小 + 各層 feature map 的最大值 + 輸出緩衝區），找出哪個部分超標，決定是縮小模型、降低解析度，還是調整編譯選項釋放空間。
2. **執行期「完全沒輸出但無錯誤」的情況，先確認是不是統計路徑跟實際處理路徑分離**：加入節流式除錯輸出（例如每 N 次呼叫印一次，避免洗版），直接在懷疑的處理函式入口和關鍵分支點印 log，確認該函式到底有沒有被呼叫到、走到了哪個分支。
3. **盤點所有固定大小的緩衝區常量**：只要輸出解析度、類別數量、或任何影響資料量的架構參數變動過，就要重新檢查下游（尤其是韌體/C 端）所有寫死的緩衝區大小常量是否還夠用，不能只看訓練端設定檔。
4. **檢查邊界檢查的失敗模式**：確認超出容量時的行為是「報錯」「截斷」還是「整個跳過」，後者是最危險也最難察覺的一種，開發階段應該盡量把它改成會發出警告的版本，上線前再視情況決定是否改回靜默跳過。

## 一般性解法 / Checklist

- [ ] 模型定案前，先算清楚權重 + 最大 feature map 緩衝區 + 輸出緩衝區的總和，對照硬體定址上限留出餘裕
- [ ] 任何解析度/輸出形狀/類別數的變動，都要連動檢查下游所有寫死的緩衝區大小常量，不只是訓練端設定檔
- [ ] 遇到「功能完全沒輸出但無錯誤訊息」時，優先假設是某處緩衝區邊界檢查靜默跳過，而不是急著懷疑模型或演算法邏輯
- [ ] 用節流式除錯 log 確認可疑函式/分支是否真的被執行到，不要只憑程式碼閱讀做判斷
- [ ] 開發階段讓邊界檢查在超限時明確警告或報錯，避免「安全的靜默失敗」掩蓋真正的問題
