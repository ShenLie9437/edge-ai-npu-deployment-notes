# 硬體算子相容性：模型架構選型前的盤點方法

## 問題現象

團隊選定一個模型架構、訓練完成、也順利匯出成 ONNX，看起來一切正常，但送進目標邊緣 NPU 平台的編譯工具鏈時卻失敗——輕則某些層被靜默降級成效能很差的 fallback 實作，重則編譯器在深處某個優化步驟直接崩潰，錯誤訊息完全看不出跟哪個設計決策有關。這種問題往往到專案後期才被發現，此時模型架構已經定型，重新設計的成本很高。

## 為什麼會發生（原理說明）

邊緣 NPU 為了在極低功耗下達到高效能，硬體電路通常只針對一組有限的運算元家族做了原生加速（最典型是卷積+池化），其餘運算元要嘛不支援、要嘛只能用效能較差的方式模擬。這造成兩層風險：

- **巨觀層級**：架構本身用到硬體完全不支援的運算類型（例如 Attention 機制在只為 CNN 設計的加速器上沒有對應電路），這類問題通常查得到文件，但容易在選架構時被忽略。
- **微觀層級**：即使用的都是「看起來被支援」的常見算子，特定的計算圖拓樸模式（例如對稱分支共用同一個上游常數節點）可能踩到工具鏈本身圖優化器的邊界案例——這類 bug 通常是廠商工具鏈沒測過的排列組合，任何文件都不會提到，只能實際跑過編譯流程才發現。

## 系統化排查步驟

1. **先建立目標硬體的運算元支援矩陣**：列出候選架構會用到的每一種運算元（卷積類型、激活函數、reshape/concat/slice 等資料搬移類算子），逐一對照硬體規格文件或官方工具鏈的算子支援清單，標記「原生支援 / 需要模擬 / 不支援」。
2. **架構定型前，先用最小化的 dummy 模型跑一次完整編譯流程**：不需要真的訓練，只要架構、輸入輸出形狀、關鍵計算圖拓樸（尤其是分支合併、對稱結構）跟真正要用的一致即可，因為多數編譯器的檢查和優化只跟計算圖結構有關，跟權重數值無關。
3. **編譯器報錯難以理解時，用二分法縮小模型範圍**：從完整模型開始，逐步刪減分支/層數，找出能重現錯誤的最小子圖，通常就能定位到是哪一種算子組合或計算圖模式觸發問題。
4. **確認是否為工具鏈本身的已知限制版本問題**：同一廠商的工具鏈不同版本、不同目標晶片型號，算子支援範圍可能不同，遇到問題先確認是否為版本落差而非架構設計錯誤。

## 一般性解法 / Checklist

- [ ] 選型前先列出目標硬體的運算元支援矩陣，涵蓋卷積類型、激活函數、資料搬移算子
- [ ] 特別留意「注意力機制」類架構是否有對應硬體加速，沒有的話評估用固定形狀的替代設計
- [ ] 架構定型前用最小化 dummy 模型跑過一次完整編譯流程，驗證計算圖結構本身能過關
- [ ] 對稱結構(例如對稱 resize、雙分支共用常數)是常見的圖優化器邊界案例，設計時可留意能否改成非對稱寫法規避
- [ ] 編譯器報錯難懂時，用二分法逐步縮減模型找出最小重現子圖，而不是對著完整模型盲猜
