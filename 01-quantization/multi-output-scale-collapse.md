# 多輸出張量合併導致的量化精度崩壞

## 問題現象

在把一個多任務模型（例如同時輸出語意分割遮罩與偵測框）匯出到邊緣 NPU 平台時，為了減少輸出節點數量（有些工具鏈對輸出節點數量有硬體開銷或數量限制），工程師常見的做法是把偵測頭的多個分支（例如置信度熱圖、框尺寸、框偏移量）用 concat 合併成一個張量再輸出。合併後模型能正常編譯、推論速度也如預期改善，但上板實測發現某幾個原本表現正常的偵測輸出精度大幅劣化，數量級上可能是原本誤差的十幾到二十幾倍，而其他輸出看起來沒事。

## 為什麼會發生（原理說明）

INT8 量化的本質是把一段浮點數值範圍線性映射到 256 個整數格點，映射所用的 scale 是「以張量為單位」決定的（通常來自校正資料集上的 min/max 統計）。當你把數值範圍差異很大的兩個分支（例如一個落在 0~1 之間，另一個落在 0~20 甚至更大）concat 成同一個張量後，工具鏈只能用「取兩者聯集」的方式算出一組共用 scale。範圍小的那個分支等於被壓縮到整個 256 格點裡極小的一段，實質可用的量化解析度大幅下降——這不是 bug，是量化演算法在「共用一組 scale」假設下的必然結果。

## 系統化排查步驟

1. **先確認是不是合併造成的**：在合併前後分別 dump 每個輸出張量在校正集上的 min/max/abs_max，如果合併後某分支的「實際數值範圍 ÷ 合併後張量的總範圍」比例很小，就是量化解析度被壓縮的直接證據。
2. **拆到子類別/子輸出層級看精度**，不要只看整體平均指標——整體可能只掉一點點，但某個原本數值範圍小的輸出可能崩得很嚴重，平均值會把這個訊號蓋掉。
3. **如果要修正合併前的數值範圍**（例如把大範圍的分支除以一個係數再合併），先確認縮放算子的實作方式：如果用 runtime 的除法/乘法算子插入計算圖，某些工具鏈的圖優化器可能無法正確處理，導致優化失敗、退回未優化圖，甚至讓後端編譯器直接崩潰或報出難以理解的錯誤。
4. **改用「烘焙進權重」的方式驗證**：把縮放係數直接乘進前一層（例如最後一層卷積）的權重張量裡，讓深度學習框架在匯出 ONNX 時透過 constant folding 把縮放吸收掉，不引入額外的 runtime 算子，再重新匯出、編譯、比較是否還有同樣的問題。

## 一般性解法 / Checklist

- [ ] 合併多個輸出前，先列出各分支的數值範圍量級，範圍差異超過一個數量級以上要特別警惕
- [ ] 需要縮放時，優先選擇「可被匯出框架 constant-fold 進權重」的寫法，避免在計算圖裡留下額外的 runtime 算子
- [ ] 精度驗證一律拆到子輸出/子類別層級，不要只看聚合指標
- [ ] 不信任靜態估算工具的數字，用真實硬體重新量測一次作為最終判斷依據
- [ ] 縮放係數要在推論端（後處理）對稱地還原回來，且雙端常數來源要有單一事實來源（避免兩處各自硬編碼、改一邊忘了改另一邊）
